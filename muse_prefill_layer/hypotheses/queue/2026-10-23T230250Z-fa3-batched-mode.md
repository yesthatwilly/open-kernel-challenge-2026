# fa3-batched-mode

## Change

Every prefill case has the same q_len for all B requests (cu_seqlens_q is 0, L, 2L, ...), so call flash_attn_with_kvcache in batched mode instead of varlen mode: q.view(batch, q_len, hq, d).to(FP8), no cu_seqlens_q and no max_seqlen_q, the same paged k_cache, v_cache, page_table and cache_seqlens, causal=True, the same window_size, the same descale kwargs, scheduler_metadata=None, num_splits left at its default (FA3's heuristic), pack_gqa left at its default; the output [B, L, hq, d] is reshaped to [T, hq*d] for FusedRMSNormGate. Everything else stays the parity path. Mechanism: with uniform seqlen_q FA3 uses its static tile scheduler and may apply its split-KV heuristic (get_num_splits) and GQA packing, which the varlen path handles with the dynamic scheduler and no split; the 753-token shapes launch only 6 m-tiles x 16 heads = 96 CTAs per request against 80K keys, below the 132 SMs, so a split with a combine kernel over [753, 16, 64] fp32 partials can fill the GPU.

## Expected

- `*layer=full load=turn_1*` faster: 96 CTAs over 80K keys on 132 SMs; split-KV or a better static schedule raises SM occupancy on ~350 us of attention
- `*layer=full load=turn_4*` flat: 384 CTAs already fill the SMs; the scheduler change alone is inside the interval
- `*layer=sliding*` flat: sliding attention is a small share of every shape
- `*load=first_turn*` flat: 2048 m-tiles fill the GPU in either mode

## Risk

Low risk: the same kernel and the same keys, only the launch mode changes; batched paged kvcache is the primary FA3 API. Failure modes: if FA3's heuristic already splits in varlen mode the result is flat everywhere and attributes nothing (that is cheap to learn); FP8 q in batched mode with page size 1 is supported as in varlen. Rules: every key attended, FP8 cache and queries unchanged, no host sync, no caching. Attribution: only the FA3 call changes.

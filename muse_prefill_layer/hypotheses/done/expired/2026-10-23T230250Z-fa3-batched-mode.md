# fa3-batched-mode

## Change

Every prefill case has the same q_len for all B requests (cu_seqlens_q is 0, L, 2L, ...), so call flash_attn_with_kvcache in batched mode instead of varlen mode: q.view(batch, q_len, hq, d).to(FP8), no cu_seqlens_q and no max_seqlen_q, the same paged k_cache, v_cache, page_table and cache_seqlens, causal=True, the same window_size, the same descale kwargs, scheduler_metadata=None, num_splits left at its default (FA3's heuristic), pack_gqa left at its default; the output [B, L, hq, d] is reshaped to [T, hq*d] for FusedRMSNormGate. Everything else stays the parity path. Mechanism: with uniform seqlen_q FA3 uses its static tile scheduler and may apply its split-KV heuristic (get_num_splits) and GQA packing, which the varlen path handles with the dynamic scheduler and no split; the 753-token shapes launch only 6 m-tiles x 16 heads = 96 CTAs per request against 80K keys, below the 132 SMs, so a split with a combine kernel over [753, 16, 64] fp32 partials can fill the GPU.

## Expected

- `*layer=full load=turn_1*` faster: 96 CTAs over 80K keys on 132 SMs; split-KV or a better static schedule raises SM occupancy on ~350 us of attention
- `*layer=full load=turn_4*` flat: 384 CTAs already fill the SMs; the scheduler change alone is inside the interval
- `*layer=sliding*` flat: sliding attention is a small share of every shape
- `*load=first_turn*` flat: 2048 m-tiles fill the GPU in either mode

## Risk

Low risk: the same kernel and the same keys, only the launch mode changes; batched paged kvcache is the primary FA3 API. Failure modes: if FA3's heuristic already splits in varlen mode the result is flat everywhere and attributes nothing (that is cheap to learn); FP8 q in batched mode with page size 1 is supported as in varlen. Rules: every key attended, FP8 cache and queries unchanged, no host sync, no caching. Attribution: only the FA3 call changes.

## Adversarial review

Reviewed 2026-10-24T071305Z by an adversarial subagent (model opus).

**Verdict: hold.** The occupancy mechanism is contradicted by the landed profile: the FA3 kernel already runs at the same ~590-606 TFLOP/s on turn_1 full (96 nominal CTAs) as on turn_4 (384) and on the 16K first-turn shapes. That leaves at most ~7 us of headroom on one weight-16 shape, roughly 30x below the +/-1.5% interval. Hold until fa3-contiguous-kv-gather resolves, because that result decides which FA3 regime a batched-mode test would even be measuring.

### Justification
Arithmetic from sglang-pipeline-parity.result.json (and the same numbers in moe-align-side-stream): turn_1 full has 753 queries x (80000 + causal) = 60.5M QK pairs x 16 heads x 64 x 4 = 248 GFLOP in 419.9 us, about 590 TFLOP/s. turn_4 full has 4x the work in 1656.1 us (599 TFLOP/s). first_turn runs at 605 (ctx 32768, 4545.7 us), 606 (ctx 65536, 8164.1 us) and 606 (ctx 0, 907 us). If turn_1 really were 96 CTAs in one under-filled wave on 132 SMs with no split, it would run at about 96/132 = 73% of the turn_4 rate (~435 TFLOP/s). It runs at 98% of that rate. So the varlen path is already filling the GPU, most likely through FA3's own get_num_splits and pack_gqa heuristics. FA3 sizes both from max_seqlen_q in varlen mode. It also forces PackGQA on a non-TMA paged KV (page_size 1), which is exactly this case. Batched mode would most likely pick the same split, the same packing and the same tile config, differing only in the Varlen template flag. The best case closes the 590 -> 600 gap: about 7 us on a weight-16 shape inside a ~72.6 ms turn_1 load, about 0.15% of that load and about 0.05% of the geomean. The `expected` entries are consistent with TASK.md weights in direction (turn_1 faster, others flat), but the size the md implies ('~350 us of attention' raised to fill the SMs) does not exist. The hypothesis names this failure mode itself ('if FA3's heuristic already splits in varlen the result is flat everywhere and attributes nothing'), and the profile already says that is the likely outcome. Weakest link: the claim that the varlen path uses the dynamic scheduler with no split and leaves turn_1 under-occupied. The measured per-FLOP throughput refutes it.

### Confounders on the current kernel
- sglang-pipeline-parity: it set the exact FA3 call this changes (paged page_size 1, varlen with cu_seqlens_q/max_seqlen_q, scheduler_metadata=None in prefill). It does not confound the measurement, because the change sits entirely inside that call and nothing else in the parity path depends on the launch mode. It is the source of the ~600 TFLOP/s evidence that makes the hypothesis unlikely to move.
- fa3-contiguous-kv-gather (in flight, not landed): if it lands, the base FA3 call becomes non-paged (page_table=None), using TMA KV loads, no forced PackGQA and a different split heuristic. Batched mode stacked on that is a pure non-varlen dense FA3 regime and a different experiment from the paged one argued here. On the current paged base the two are separable (different parameters, different mechanism), but a paged batched-mode result would become irrelevant the moment contiguous-gather is promoted.

### Interference and A/B needs
No companion would make a single run interpretable, because the most likely result (flat on every shape) is unambiguous already: batched and varlen pick the same kernel configuration. A control that pins num_splits=1 in varlen mode would only confirm that varlen already splits, and the profile throughput already strongly implies that. The one decisive piece of information is free and needs no scored run: list the kernels for turn_1 full in a profile. A flash_fwd_combine / FlashAttnFwdCombine kernel shows that varlen already splits; result.json top_kernels is truncated to four and cannot show it. The more valuable form of this idea waits for fa3-contiguous-kv-gather: if it lands, re-mint as 'fa3-batched-mode on contiguous' with depends_on: fa3-contiguous-kv-gather, where uniform seqlen_q plus a dense KV could enable TMA/static scheduling that the varlen path lacks. If it does not land, the paged batched-mode test is worth at most ~0.05% and does not justify a run from the daily quota.

### Open questions
- Does the varlen FA3 call on turn_1 full already launch a combine kernel (num_splits > 1)? Check a full kernel list for that shape, not the truncated top-4 in result.json.
- Is ~600 TFLOP/s the FA3 FP8 hdim-64 paged ceiling on H200 (page_size 1 forces cp.async KV gathers, not TMA)? If so, the attention headroom on every full shape is in KV loading (the contiguous-gather mechanism), not scheduling.
- If fa3-contiguous-kv-gather is promoted, does the dense FA3 path with uniform seqlen_q choose a different tile/split than varlen? That is the only setting where batched mode could plausibly separate from varlen.

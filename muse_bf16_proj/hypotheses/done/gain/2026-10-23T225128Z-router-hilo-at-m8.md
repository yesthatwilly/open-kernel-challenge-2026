# router-hilo-at-m8

## Change

In kernel_fn's router branch, lower the threshold at which the router switches from F.linear(x.float(), router) to the BF16 hi + lo pair: change ROUTER_FP32_MAX_TOKENS from 8 to 1, so m=8 (and the m=7/m=9 tests) take the two torch.mm(x, router_hi_t/router_lo_t, out_dtype=torch.float32) GEMMs that the parity base already builds in prepare(), while m=1 keeps the FP32 F.linear path exactly as before. Nothing else changes: the bf16 layers, prepare(), and the hi/lo tensors stay as in sglang-gemm-dispatch-parity. Mechanism: at m=8 the FP32 path runs two sm80_xmma f32 SIMT GEMM kernels (9.3 + 8.3 us) plus the x.float() cast (2.2 us) for 26.6 us reported; the hi/lo path at m=16 runs two nvjet bf16 tensor-core splitK GEMMs + two splitKreduce + one add for 14.8 us. m=8 should land near the m=16 number. The rules allow hi/lo with FP32 accumulation at any batch size.

## Expected

- `layer=router load=verify_1 *` faster: m=8 leaves the 26.6 us fp32 xmma SIMT path for the ~15 us bf16 hi/lo tensor-core path; verify_1 load is 76 us total so this is ~15% of the load
- `layer=router load=decode_1 *` flat: m=1 stays on F.linear fp32 gemv (threshold is 1, not 0); control
- `layer=router load=decode_16 *` flat: m=16 already on the hi/lo path; control
- `*layer=pooler*` flat: untouched bf16 layer; control

## Risk

Correctness: the m=8 router test and the m=9 outliers test now run on hi/lo; L2 tol is 1e-4 and probe rows 1e-3, and hi+lo residual is ~2^-16 relative per weight, so margin is ~10x on both. The m=7 pooler test is unaffected. If the m=8 hi/lo path were slower than expected it would show only on verify_1. The reviewer of the parity run named this as the first real hypothesis; it is deliberately the smallest possible step (threshold 8 to 1) so the m=1 gemv path is left as a control; m=1 on hi/lo is a separate question (five launches vs three).

## Adversarial review

Reviewed 2026-10-23T230253Z by an adversarial Fable subagent (model fable).

**Verdict: proceed.** A one-constant change (ROUTER_FP32_MAX_TOKENS 8 -> 1) that moves exactly one scored shape, router verify_1 m=8, from the 26.1 us fp32 SIMT path onto the hi/lo tensor-core path the parent already runs at m=16 (14.5 us). Expected ~1.18x on the verify_1 load, ~1.028x on the 6-load geomean, outside the +/-1.5% interval; the per-shape attribution isolates it with no companion run.

### Justification
Mechanism is plausible and directly supported by the parent's own profile (job 017804b34fed40b3): router verify_1 m=8 is 26.14 us on the parent vs SGLang 26.13 us, made of two sm80_xmma_gemm_f32f32 SIMT kernels (9.3 + 8.2 us) plus the 2.3 us x.float() cast, against a 1.8 us floor; the hi/lo path at m=16 is 14.51 us (nvjet_sm90_tss_64x16 splitK 8.1 + splitKreduce 3.6 + vectorized add 0.9, with the second GEMM+reduce below the top-3 cut) and 15.14 us at m=32. cuBLAS tile choice at m=8 vs m=16 is nearly identical on the bf16 layers (qkv_gate 14.04 vs 13.89 us, pooler 21.28 vs 21.45 us), so landing near 14.5 us at m=8 is a fair prior. Shape arithmetic: verify_1 load = 14.04+7.01+21.28+6.84+26.14 = 75.3 us; replacing 26.14 with ~14.5 gives 63.7 us, a 1.18x load gain and a 1.028x geomean over the six equally weighted loads, i.e. ~2x the half-width of the interval; a flat result would be a clear negative. The expected globs are consistent with TASK.md: all weights are 62, each load counts equally, and only verify_1 contains an m=8 shape. Weakest link: the assumption that cuBLASLt's heuristic for bf16 [8,8192] x [8192,256] with fp32 output chooses a splitK nvjet kernel as it does at m=16/32; N=256 with a 64x8 tile and no splitK would be only 4 CTAs streaming 4.2 MB per GEMM and could be slower than the SIMT path. Even then the result is interpretable (per-shape). Second weak point, cosmetic: the hypothesis text says the m=7 and m=9 tests move to hi/lo; m=7 is a pooler test and m=9 (router, outliers) is already above the parent's threshold of 8 and passed on hi/lo in the parent run, so only the m=8 router test actually changes path, which lowers the correctness risk below what the body claims. Note that even the target hi/lo path sits at ~8x the 1.8 us floor (0.5 TB/s effective); this hypothesis recovers the SIMT-vs-tensor-core gap, not the launch/splitK overhead, which router-triton-hilo-fused targets.

### Confounders on the current kernel
- sglang-gemm-dispatch-parity (parent, not yet promoted but the build base): this change is a constant inside the parent's router branch and depends on the parent's router_hi_t/router_lo_t tensors; it cannot exist without it. It does not confound: the parent left router verify_1 at 26.14 us == SGLang 26.13 us (0.9994x) and every other shape within noise, so any movement on router verify_1 is the threshold alone, and no other shape's path changes.
- No other hypothesis has landed on master (landed list is empty), so there is no cross-area interaction, no shared launch sequence and no shared memory traffic to disentangle.

### Interference and A/B needs
No companion is warranted. ab-revert of the parent is not implementable (the change requires the parent's hi/lo tensors) and would only re-measure the starter. ab-tune of the parent's only knob is this hypothesis itself; the next tune (threshold 0, hi/lo at m=1) is a separate question the parity reviewer already named and is not needed to read this result, because m=1 (decode_1) is kept on the untouched F.linear path as a built-in control. A sub-change control is unnecessary: there is one sub-change and the judge reports per shape, so a gain shows as router verify_1 dropping from ~26 us toward ~15 us with decode_1/decode_16/decode_32/verify_16/verify_32 router and all 25 bf16 shapes flat, and a loss shows as router verify_1 rising, which would mean cuBLAS's m=8 bf16 heuristic is worse than the SIMT path and is itself a learning. Neither outcome is ambiguous.

### Open questions
- Does cuBLASLt choose a splitK nvjet kernel for bf16 m=8, N=256, K=8192 with fp32 output, or a non-splitK tile with only 4 CTAs? Read the run's profile for router verify_1: if the kernel is not splitK and the shape lands above ~20 us, the hi/lo path itself needs the Triton fused kernel at m=8, not the cuBLAS one.
- The hypothesis body misstates the tests that move: only the m=8 router test changes path (m=7 is pooler; m=9 router was already on hi/lo under the parent). Fix the text before harvest so the attribution record is accurate.
- Follow-up once this lands: threshold 0 (hi/lo at m=1, decode_1 router at 10.4 us vs 1.8 us floor, currently dot_kernel 4.1 + cast 2.0 + reduce 1.6 us). It trades 3 launches for 5 under graph replay and needs the probe-row bound checked at m=1 where hi/lo error cannot average out; a separate hypothesis, not a companion of this one.
- Ordering with router-triton-hilo-fused: that hypothesis replaces the whole router branch at every m and would subsume this one; if both run, build triton on top of this so the m=8 attribution stays sequential rather than overlapping.

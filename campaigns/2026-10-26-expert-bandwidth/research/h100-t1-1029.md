## Q1: is K2's w2 already prefetched before the PDL wait?

### What the code says (read before any run)

`rewrite/lib/cuda/ea6_kernels.cuh` (eb-v4x256c), K2 producer warp 8, lines 153-158:
`for (int i = 0; i < pre; ++i) issue(i);  // weights do not depend on K1` and then `griddep_wait();`, with
`pre = min(r, D2)`, `D2 = 2`. So **K2 already issues its first 2 w2 records (2 x 36,864 B per CTA) by TMA before
griddepcontrol.wait.** The design panel is right on that. The consumers (warps 0-7) and the epilogue wait on
griddepcontrol first, because they need K1's h. Records 2..r-1 are issued only when a consumer frees a ring slot, so
**they stream after K1 ends.** K2 serves one expert per CTA (132 / n CTAs per expert, 256 records per expert), so
r = 3.9 / 5.8 / 7.8 records per CTA at n = 2 / 3 / 4. The pre-wait prefetch covers ~51% / ~34% / ~26% of the w2
bytes. The rest is what the node anatomy saw as w2 waiting (~3.4 us of tail per expert). Both readings are partly
true. The ring cannot get deeper while K2 stays co-resident: K1 127,328 B + K2 D2 90,448 B = 217,776 of 233,472 B
per SM, and D2 = 3 would need 127,312 B.

So the only way to move more w2 bytes before the wait is a prefetch that needs no shared memory: an **L2 prefetch
of records pre..r-1, issued by K2's producer before griddepcontrol.wait**. The expert ids come from topk_ids
(build_map), not from K1, so this is legal. Prior art differs: [node-only] m07 (CLAIMS) prefetched w2 from v1's
K1 after its last w13 copy and was 2-3% slower. Here K2 prefetches only its own records, ~13-28 us before it needs
them, in the window where K1 uses ~2.0 of 3.11 TB/s.

### The variant (node-only; scratch `/home/user/git-scratch-c24a6e/t1-1029/`)

Built from eb-v4x256c's rewrite with `patch_kernel.py` + `patch_core.py` (submission 908,971 B, sha256 a1f30d2a).
Default behaviour is master's: K2 flag bits are 0 unless the module knob `EA6_K2PF` is set, and it is read at launch,
so a `cap` freezes it into one arm's graph.
- K2 flag 16 `pf`: before the wait, lanes 0-31 of the producer issue `cp.async.bulk.prefetch.L2.global` for every
  4608-B piece of records pre..r-1.
- K2 flag 48 `pfel`: the same with an `L2::cache_hint` evict_last policy (`createpolicy.fractional`). These are new
  PTX forms on the judge.
- K2 flag 64 `pfln`: the same bytes with per-128-B-line `prefetch.global.L2`, the form already run on the judge.
- Stamps (prepare-only debug buffer, DBG 8 -> 16, %globaltimer): K2 entry, prefetch issued, wait returned, whether
  records 0 / 1 were already full when the wait returned (`mbarrier.try_wait`, non-blocking), first post-wait issue,
  last issue, first consumer full, last consume, last epilogue. `_ea6_anat_pf` runs v6pe (fast bits 7) at n = 1..4 for
  each mode, 5 eager synced runs per cell after a read flush, and prints `[ea6] anatpf` lines in prepare.

### Pre-registered decision rules (written 05:10Z, before any run)

**Q1a (settle).** From the mode-0 stamps (= master's behaviour) at n = 2 and 3, in both replicates:
- "Prefetched before the wait" is TRUE if records 0 and 1 are full when the wait returns on >= 90% of K2 CTAs [cyc].
- "w2 waits on griddepcontrol" is TRUE for the rest if the post-wait K2 time per CTA grows with r and is >= 0.7 us
  per record [hbm-ish on the node; the slope is reported as us/record].

**Q1b (the variant).** In-process R3a on master's inputs: arms of the variant (forced v6pe at modes 0 / 16 / 48 / 64)
and board+v6pe as the null, decode 1 only, routing control k_local 1..4 (200 reps per k), two replicates on
different GPUs. The rotation gives each party every position, so both orders are covered.
- Node metric: the per-k paired ratio vs variant-mode-0, and the delta of the per-k medians in us, weighted by
  EA6_W1 (n2 .475, n3 .43, n4 .085; n1 is reported with weight 0).
- Transfer: the absolute node delta is [hbm]. The judge estimate scales the node delta at each n by
  judge_tail(n) / node_tail(n), where tail = row minus K1 alone. Judge (af154932 kernel-only): n2 22.62 - 15.49 =
  7.1 us, n3 32.10 - 20.74 = 11.4 us. Node: from the mode-0 stamps (K2end - K1end + combine) or nsys. The stamps'
  post-wait us/record ratio (arm / mode 0) is the [cyc]-like part, quoted with it.
- **GO for a judge-check build:** estimated judge weighted delta >= 4.0 us (~2.5% headline); and the arm resolves
  faster at n2 and at n3 in both replicates (interval clear of 1 by the 0.003 MDE); and no n is resolved slower; and
  memcheck + synccheck are clean.
- **MID** (1.5-4.0 us estimated, or resolved in only one replicate): build only as a raced arm riding another T=1
  build.
- **KILL:** < 1.5 us estimated, or slower at n2 or n3 in either replicate. Record it as [refuted] or [node-only].
- The null (board+v6pe vs variant mode 0) must read inside +-0.5%, or every Q1b row is VOID (the patch itself would
  then cost time).

**Q2 (R0 ring depth, when eb-v6deep lands).** v6K1 D3/D4/D5 at n = 2, 3, 4 and K2 D2/D3/D5, kernel-only, read
flush, on one GPU. Report rec(D5) / rec(D3) per record [cyc-like ratio]. The R0 spec's rules apply as written (GO <=
0.87-0.90 x and <= 1.17-1.20 us; KILL >= 0.95 x). The node's absolute us are [hbm] and are not decision data.

### 2026-10-29T0550Z: CORRECTION to the Q1a / Q1 / Q2 reading above ("consume-bound" was wrong on the node)

The node's per-record rates are its HBM bandwidth. 132 CTAs x 36,864 B per record, every 1.50-1.66 us, is

## Q4: ea6 consume-rate microbench at T=1 (pre-registered 2026-10-29T0610Z, before any run)

**Variant** (node-only; `patch_cb.py` on master's tree; submission 912,147 B, sha256 2f6239e4). Default paths are
byte-for-byte master's behaviour.
- `eak6::ea6_kernel` gets a 5th template parameter CV, the consume variant:
  - 0: board dq2 + X1;
  - 1: dq2 with XB=0;
  - 2: DQ1, XB=0;
  - 3: no dequant (same loads and X1 fragments; raw words to the MMA).
- K flag 128 "consume-only": past the first min(r, D) real TMA loads, the producer completes the slot's full barrier
  with a plain arrive. The consumers then re-read resident shared memory, and HBM is out of the loop.
- `_ea6_cbench` (prepare) graph-times 14 configs at forced n = 2 / 3 / 4 (T=1, read flush, 21 reps x 2 rounds).
  Per-record time per CTA = slope(n2 -> n4) x grid / 512 (K1) or / 256 (K2); per-SM rate = records per us per SM.
- Configs:
  - K1 normal / consume-only;
  - consume-only on 66 CTAs (per-CTA invariance check);
  - D1 instance at 1 and 2 CTAs per SM (8 vs 16 consumer warps per SM);
  - dequant paths xb0 / dq1 / nodq;
  - nodq at 2 CTAs/SM;
  - K2 normal / consume-only / D1 x2 / nodq.

**Decision rules** [cyc; the node's 1.83 GHz SM clock is scaled to the judge's 1.98 GHz by x0.924]:
- Let rc = the consume-only per-record time of the board's K1 (`K1c`), judge-scaled. Judge K1 rec = 1.31-1.37 us
  (R0 anatomy); judge K2 = ~1.30.
  - rc >= 1.18 us (>= 0.9 x 1.31): the judge's T=1 is **consume-bound**, and the consume rate is the lever.
  - rc <= 0.98 us (<= 0.75 x 1.31): the judge is **bandwidth / latency-bound**, and the consume rate is not the lever
    (the bytes or the HBM efficiency are).
  - In between: mixed. Both matter, and the headroom from the consume side is 1.31 - rc.
- A knob **moves the rate** if its consume-only per-SM rate differs from `K1c`'s by >= 10% in both rounds of both
  replicates. Reported as a % per knob: warps (D1 x2 vs D1), dequant (nodq / xb0 / dq1 vs board), and K2 vs K1.
- Check: `K1c g66` must match `K1c` per CTA within 5%, or the per-CTA reading is VOID (a shared resource such as L2
  would then be binding).

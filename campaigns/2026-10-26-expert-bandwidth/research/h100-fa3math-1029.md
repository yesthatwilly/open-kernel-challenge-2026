## Question and decision rule (pre-registered by the caller)

Can the gate's math get >= 1.2x faster (math-only <= ~195 us at v32) via (a) a C7513-free warp-specialized build or
(b) a non-WS form with two interleaved QK/softmax/PV chains per warpgroup? e2e <= 0.78 at v16 and v32 with tolerance
held -> attention judge-check build for 10-30; math-only 1.0-1.2x faster -> report and stop; no C75xx-free form ->
record the trigger and stop.

## Verdict

**No. The serialization is fixed, but the result is still slower than the gate.** The C75xx-free WS kernel runs math-only
at **287-304 us at v32** (gate **237**) and **148-161 us at v16** (gate **121-125**): 0.78-0.83x the gate's speed, below
the 1.0x floor of the decision rule. e2e is **1.07x master at v32** and **1.04x at v16** (the gate: 0.82 / 0.83). No judge
check. (b) was not built; the evidence below predicts it would not beat the gate either.

## Step 1: the trigger (CPU builds, one cubin per variant; `bin/fa3math/bisect/SUMMARY.txt` in the bundle)

The fa3ws v7b kernels actually drew **C7514** ("non wgmma instructions *reading accumulator* registers ... between start
and end of the pipeline stage"). v7a drew C7513. The cause was:

```
if (have_p) wg_wait<1>(); else wg_wait<0>();   // tile 0 of each request: only QK committed
```

The number of pending groups depends on the path. At the join, ptxas cannot prove that QK(r) retired before softmax reads
S, so it serializes every wgmma. **Fix (BX 1):** commit an empty group (`wgmma.commit_group` with no wgmma) on the
no-PV path and always `wait<1>`.

| variant (fa3s<64,8,MODE 0>, BX bits) | C75xx | HGMMA / DEPBAR gsb0 0x0 / 0x1 |
|---|---|---|
| 0 baseline (v7b) | C7514 | 12 / 14 / 0 |
| **1 uniform wait (empty commit group)** | **none** | 13 / 3 / 1 |
| 2 O rescale moved after wait<0> | C7514 | 12 / 14 / 0 |
| 4 operand fences in CUTLASS order | C7514 | 12 / 14 / 0 |
| 16 no setmaxnreg | C7514 | 12 / 14 / 0 |
| 32 no operand fences at all | C7514 | 12 / 14 / 0 |
| 128 no request-boundary flush | C7514 + C7517 | 8 / 10 / 0 |
| 8 always wait<0> (control) / 64 no softmax (control) | none | - |
| 3, 7 (1 + others), MODE 3 bx 3 | none | 13 / 3 / 1 |

Not the trigger: register writes while wgmma is in flight (the O rescale during QK), fence placement, setmaxnreg,
register pressure (168 regs, no spills either way). In the full library every ORD/BX-1 instantiation (all MODEs, TK 64
and 128) is C75xx-free. The gate's MODE 3 C7519 (`WG.AR in divergent path`, constant Q) is a separate warning.
The rule to carry over: **the wgmma wait depth must be the same on every control path that reaches a read of the
accumulators.** Pad with empty commit groups.

## Why (b) was not built

- The gate uses 108 registers at 2 CTAs/SM. A second independent chain needs another O[32] + S[32] (+64 regs), so about
  170 regs. That allows only 1 CTA/SM, which still holds 4 chains per SM, now on 8 warps instead of 16.
- WS bx3 already is this shape: 2 consumer warpgroups, each with QK(r+1) overlapped against softmax/PV(r), no
  serialization. It measured 287 us against the gate's 237. Swapping thread-level parallelism for intra-warp overlap
  loses here, because the per-tile chain is latency-bound (issue ~52 %).
- A two-chain form that keeps 2 CTAs/SM does not fit in 128 regs without spills. Predicted: no better than the gate
  (projection, not measured).

## What transfers to the H200

- Transfers: the trigger and the fix (same ptxas, sm_90a), C75xx status, instruction/wait counts, the per-SM math times
  (gate 237, WS 287-304 us at v32), and all precision numbers.
- Does not transfer: loads-only and the ceiling (the H100's 2.79 TB/s).
- The gate's e2e (0.82-0.83x master) remains the best full-verify form. It is math/latency-bound at the memory-ceiling
  time. Further gains need fewer instructions per tile, not more overlap.

## Question and decision rule (pre-registered by the caller)

Does FA3-style warp specialization make the math ~1.3x faster than the ceiling rate, so e2e reaches <= 0.78x master at
v16 / v32? <= 0.78 with tolerance held: judge check, then a decode port; 0.78-0.85: report the limit; no better than the
gate (>= 0.82): warp specialization does not pay here, report why.

## Verdict

**No better than the gate: e2e 1.12-1.16x master (slower than master), vs the gate's 0.82-0.83.** Warp specialization does
not pay in this form. The memory half works (the producer warpgroup alone, 1 CTA/SM, 64-144 KB in flight, moves
2.74-2.80 TB/s = the ceiling). The math half is **1.46x slower** than the gate's math-only kernel, and the reason is a
compiler one: **ptxas serialized every wgmma in every warp-specialized kernel** (C7513 "wgmma.mma_async instructions
are serialized due to non wgmma instructions defining input registers of a wgmma between start and end of the pipeline
stage"). In SASS each HGMMA is followed by `WARPGROUP.DEPBAR.LE gsb0, 0x0`, so there is no QK/softmax/PV overlap at all,
and with 2 consumer warpgroups per SM (8 warps) instead of the gate's 4 (16 warps), the latency is exposed. One rebuild
in FA3's exact IntraWGOverlap order (P converted only after wait<0>, Q reloaded only with nothing in flight, O rescaled
while QK runs) **still drew C7513** and measured the same. The pre-registered question (does *working* intra-warpgroup
overlap speed up the math 1.3x) is therefore **not answered**: what was measured is warp specialization without overlap.

## Kernel (v7, `fa3s_kernel<TK, NS, MODE, ORD, FN, 56, 224>`)

- 1 CTA/SM, 384 threads. WG0 producer (`setmaxnreg.dec 56`): page-index ring by cp.async NS tiles ahead; K/V cp.async ring
  of NS stages x TK keys x 256 B (fa3gate's swizzled rows); per tile each producer thread does
  `cp.async.mbarrier.arrive.noinc` on full[slot] (count 128, the producer never waits on its own loads) and waits
  empty[slot] (count 8 = consumer warps). WG1/WG2 consumers (`setmaxnreg.inc 224`), one per KV head: QK wgmma
  m64n64k32 e4m3 from the ring (consumer-side proxy fence), V widened to f16 into a per-WG double buffer, ex2.f16x2
  softmax, PV wgmma m64n64k16 f16; one mbarrier wait + one 128-thread named barrier per tile; no `__syncthreads`.
  Partials + the gate's grid-barrier combine (consumer warps). ptxas: 168 regs at launch, no spills (TK 128: 128 B stack).
- v7a: QK(i+1) issued before (ORD 0) or after (ORD 1) softmax(i), P double-buffered. v7b (final): FA3 order.

## Why (no ncu run: the SASS answers it)

- C7513 hit every `fa3s_kernel` instantiation, and also the gate's own `fa3y` MODE 3 (math-only) kernel and the older
  fa3w/fa3x/fa3z kernels, but **not** the gate's MODE 0/1 kernels, which issue wgmma only when nothing is in flight
  (no register written while a wgmma is outstanding). Any schedule that writes softmax/rescale registers while a wgmma
  is in flight, which is the whole point of intra-warpgroup overlap, tripped it here, including FA3's own order.
- Without overlap, each consumer warp runs a serial per-tile chain (QK -> wait -> softmax -> PV -> wait): ~340 us x
  1.98 GHz / ~305 tiles ~ 2200 cycles per tile per warpgroup, with only 2 consumer warps per scheduler to hide it.
  The gate interleaves 4 warpgroups (2 CTAs x 2) per SM, so its 3000-cycle chains overlap 2-way: ~1500 cycles per tile.

## What would answer the question (not done: the wrap-up budget allowed one rebuild)

1. Find the C7513 trigger: compile a minimal QK -> softmax -> PV loop and bisect what writes an input register
   mid-stage (candidates: the `asm volatile "+f"` operand pins between wgmmas, the 64-bit descriptor adds, the
   per-lane conditional mask writes on S). CUTLASS's `warpgroup_fence_operand` and `wgmma.fence` placement are the
   reference. Pass bar: no C7513 and HGMMA groups waited with `DEPBAR.LE gsb0, 0x1`.
2. Only then re-measure math-only; it needs <= ~180 us at v32 (1.3x faster than the ceiling) for e2e <= 0.78.
3. Cheaper alternative inside the gate's 2-CTA layout: keep 4 consumer warpgroups per SM (producer warp + 2 x 2 consumer
   WGs = 640 threads), so warp-level parallelism hides latency even if overlap stays serialized.

## 2. al: `ms_align` (CUDA)

- **Layout:** grid 33 x 256 threads, the same outputs and grid shape as the Triton kernel.
  - Every CTA loads the ids, 8 independent loads in flight per thread, into shared local ids.
  - It builds a warp-aggregated histogram (`__match_any_sync` + one smem atomic per peer group).
  - Warp 0 scans the padded class starts.
  - CTA e < 32 ranks expert e's routes with one block scan over contiguous per-thread runs (ascending order) and
    writes them, plus its padding and its block_experts.
  - CTA 32 writes the local / cold ids, the sentinels past each class and the -1 blocks, then n_padded.
- **First version (run 190321):** the histogram loop issued its global loads one per iteration: **5.54 us**.
  Hoisting the 8 loads into registers (run 190712) gave **3.33 us**.
- **Exactness:** each prepare compares every output tensor (local ids, cold ids, both sorted_ids, both block_experts,
  both n_padded) with `torch.equal` against `_hm_align`. The cases are the 9 `_ea_routings` kinds plus 3 judge draws
  at T=256, at each of H -16 / -8 / 32: 33 cases. Then the T=256 p50 draw is checked against the host reference
  `_hm_align_cmp`. **BIT-IDENTICAL in all 3 prepares.** The race also checks that the graph and eager kernel_fn
  outputs of `al` equal base's bitwise.
- **Routing:** `[mstack]` is the last prepare phase, after `[ea-enc]`. It runs per hybrid T: build (background
  thread from 0 s, ~36 s, parallel with the other modules), then exactness, then the race. If the build fails,
  exactness fails, or the phase raises, it falls back to master's Triton align. After the pick there is a
  `_wg_copy_tree` state-copy check.

## 3. cp: `ea_combine` on the hybrid tail, and whether it is rules-clean

Earlier note: h100-glue-1029.md `cp` (x1.016 node, "not bitwise"); LOG line 157 "T=256 ea_combine post-norm (x1.016,
not bitwise)".

**Rules check: clean.**
- **Same computation:** `out[t] = sum_s g * rmsnorm(y * (1 + w))`, the TASK.md formula.
- **Same input and output precision:** y is read as BF16 (the same `cache3` rows) and out is written as BF16.
- **No reduced-precision shortcut:** all math is fp32. `(1 + w)` is formed in fp32 from the BF16 weight. SGLang's
  path instead feeds a BF16-rounded `(1 + w)` (`state["norm_w"]`).
- **Closer to the reference:** rel-L2 vs the fp32 reference is 0.00386 for cp vs 0.00426 for SGLang's post-norm
  (worst row 0.00416 vs 0.00456), on both the p50 and skewed-4hot draws, in all 3 prepares. The bound is 0.015.
- **Already the scored path:** this exact kernel already runs on the board at T=8..128 (judge profile 922ddf4c rows
  1-4).
- "Not bitwise" only means it differs from SGLang's rounding. technical-rules.llms.txt and TASK.md need tolerance,
  BF16 activations and unchanged weight precision. They do not require bit-equality with SGLang.
- **Gate in prepare:** `_rt_check` (half the judge's bounds) and rel <= 2x the post-norm's own error, then the race.

**Node caveat:** nodejudge replaces SGLang's `muse_spark_v12` post-norm with a **shim** (8.7 us iso here, vs 5.6 us
for the real kernel on the judge). The node therefore overstates cp. The prepare race on the judge will time the real
kernel.
